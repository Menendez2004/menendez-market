# Handoff Template

Copy the content of the four-backtick block between the `BEGIN TEMPLATE`
and `END TEMPLATE` markers (without the outer fence) into the new
`.handoff.md` file, then fill it in.

Rules for using the template:

- Keep every heading exactly as written (English, same level, same order).
  The validator and receiving sessions locate content by these headings.
  Write the prose under them in the user's language.
- Repeat the `## Endpoint N — METHOD /path` block once per endpoint, numbered
  from 1 in the same order as `endpoints` in the front matter.
- Never delete a section because it does not apply. Write `None.` under it
  (for example `#### Query parameters` → `None.`) so the receiver knows it
  was checked, not forgotten.
- Text in `<angle brackets>` is an instruction; replace it. Remove the
  HTML comments (`<!-- ... -->`) once the section is filled.
- Unknown or undecided values are written as `TBD` and listed under
  `## Open questions` with an id (`Q1`, `Q2`...) that the `TBD` references:
  `TBD (Q2)`.

## Front matter fields

| Field | Required | Values |
|---|---|---|
| `handoff` | yes | always `api` |
| `title` | yes | short feature name |
| `direction` | yes | `backend-to-frontend` (Mode A) or `frontend-to-backend` (Mode B) |
| `receiver` | yes | `frontend` or `backend` (the side that must act) |
| `status` | yes | `draft` (open questions remain) or `ready` (implementable as is) |
| `revision` | yes | integer, starts at `1`, +1 on every revision |
| `created`, `updated` | yes | `YYYY-MM-DD` |
| `author` | yes | who wrote it (person or "Claude session for <person>") |
| `source.repo` | yes | repo the contract was extracted from |
| `source.branch` | yes | branch name |
| `source.commit` | yes | short SHA, or `uncommitted` |
| `related` | no | links: ticket, PR, design, other handoffs |
| `endpoints[]` | yes | one item per endpoint: `id` (`EP1`...), `method`, `path`, `change` (`new`, `changed`, `existing`) |

## Notes per direction

**`backend-to-frontend` (Mode A):** everything is extracted from code that
exists. `TBD` should be rare — it means the code itself is ambiguous (for
example an unhandled error path). `Receiver notes` focuses on UI states and
how to call the endpoint from the frontend's existing API client.

**`frontend-to-backend` (Mode B):** the endpoint is a request. Mark it
`change: new` (or `changed` with the diff in Purpose). The body and
response tables describe what the frontend needs; anything the backend
should decide (status codes for edge cases, limits, naming) is `TBD (Qn)`.
`Receiver notes` lists the business rules, validation and authorization
the frontend expects, and the existing backend conventions the new
endpoint should follow (copied from neighboring endpoints).
